# 可编程文件自动化工具：架构审查与修订报告

**版本：v0.2 · 替代上一版架构基线**  
**审查日期：2026-09-22**  
**范围：macOS / Windows / Linux；Rust；CLI / Agent 优先；暂不设计 GUI、移动端和本地模型实现。**

> 本报告直接修订此前方案，而非另列一个备选架构。项目尚未实现，文中的配置、JS API、错误码和命令均为拟定契约，不是现有软件功能。此次完成了设计审查与上游文档核对；未完成 Rust 原型、跨平台运行、故障注入或性能测试。参数默认值须在原型中校准。

## 一、审查结论

**保留技术方向，但需要先补执行语义，再扩展功能。**

Rust + `notify` + `rquickjs` + 轻量 YAML + JavaScript 仍然适合当前目标。不建议重新选语言，也不建议现在加入完整权限系统、插件市场或工作流平台。

原方案最需要调整的不是库，而是以下三个假设：

1. **任意 JavaScript 不能静态转换成一份完整、可编辑的声明式规则。** 应统一的是规则注册模型和每次求值的动作结果，不是强行将任意代码还原为条件树。
2. **文件事件和稳定窗口不能证明文件写入完成。** 监听只能提供线索，扫描、就绪检查、执行前复核才组成可用的处理链。
3. **有 Action Plan 不等于有事务、幂等或 Undo。** 这些需要逐项定义；数据库也不能与任意文件操作、外部命令自动构成一个事务。

修订后的首版定位：

> **一个由 Agent 易于配置、简单任务用 YAML、复杂任务用 JS，并能解释“将做什么、已做什么、哪里失败”的本地文件自动化工具。**

文档识别和收入潜力保留为后续验证方向，不作为第一版已经成立的商业结论。

## 二、变更汇总

P0 表示首次开放真实文件写操作前必须解决；P1 表示早期产品化需要解决；P2 表示延后。

| 级别 | 原方案的问题 | 本次直接修改 |
|---|---|---|
| P0 | YAML、任意 JS 都被描述为可转换成相同静态 IR | 分成 `RuleDefinition`、动态 `Evaluator`、具体 `ActionPlan` 三层 |
| P0 | `file.ready` 容易被理解为文件已完整 | 明确定义为“符合配置的就绪策略”，默认只是稳定性启发式 |
| P0 | SQLite、防重复、恢复机制被放到后续阶段 | 最小任务表、操作日志、单实例锁、扫描补偿进入 MVP |
| P0 | 多条规则同时命中后的顺序不明确 | 首版按配置顺序，首个非空计划认领文件；不隐式串联规则 |
| P0 | `run` 与 `match/actions` 的关系模糊 | 两种入口互斥；`run` 只是合并求值，不是直接执行入口 |
| P0 | 动作中的旧字符串路径在 move/rename 后失效 | 使用 `FileRef` 跟踪同一文件；`exec` 支持延迟解析文件路径参数 |
| P0 | `plan` 之后文件变化仍可能执行旧结果 | 计划绑定输入指纹、规则修订和前置条件；执行前复核 |
| P0 | 默认可以回滚所有动作 | 改成按动作分类的恢复与补偿，不承诺通用事务或通用 Undo |
| P0 | `exec` 可能在重试中重复产生外部副作用 | 默认不自动重试不确定的外部命令；失败保留现场与日志 |
| P0 | 从 JS 导出值读取版本，才能决定如何加载 JS | manifest 提前声明 API 版本；JS 常量作为一致性断言 |
| P0 | `serde_yaml` 被列为新项目默认依赖 | 替换为 `yaml_serde` 候选；锁定版本后测试 YAML 子集 [S1][S2] |
| P1 | “超过 7 天”之类条件仅依靠文件变化触发 | 增加定期规则重评估；与只找差异的扫描补偿区分 |
| P1 | Rust 跨平台被等同于整套原生依赖可稳定发布 | `rquickjs` / C 工具链与真实桌面平台测试进入技术门槛 [S4] |
| P1 | `.d.ts` 被等同于内置 TypeScript 检查能力 | 首版运行 ESM JavaScript；类型声明与可选外部检查分开 |
| P1 | 本地优先、dry-run 的网络和费用行为不明确 | 分开校验、离线预览、显式内容提取和实际动作执行 |
| P1 | 扩展名、日期、金额、空值模型前后不一致 | 统一字段契约；日期使用字符串；缺失值不猜测；金额精确表示 |
| P1 | API adapter 被认为可以低成本无限兼容 | 明确语义兼容、能力检查、黄金样例和有期限的支持政策 |
| P2 | 首版有过多动作、crate、provider、商业文档类型 | 收缩到文件级流水线；永久删除、系统通知、模型等延后 |

## 三、确定保留与明确不做

### 保留

主程序使用 Rust。桌面文件事件用 `notify`；JS 运行时优先验证 `rquickjs` / QuickJS-NG；简单配置用 YAML；状态存储使用本机 SQLite。主要入口是 CLI，Agent 通过有版本的 JSON 输出、错误码、schema 和例子使用它。

不嵌入 Node.js，不承诺 npm、浏览器或 Node API 兼容。`rquickjs` 明确不以提供系统 API 和 Web API 为目标，宿主应自行暴露需要的能力。[S4]

### 首版不做

GUI、移动端、云同步、团队服务、插件市场、远程模块下载、完整权限 UI、恶意脚本沙箱、内置大模型、任意 DAG 工作流和所有动作可撤销。

**不做复杂权限，不等于不做资源预算和误操作保护。** 前者可以延期；脚本死循环、磁盘写满、目标覆盖和重复执行属于产品可靠性，不宜延期。

## 四、修订后的架构

```text
配置文件 / Agent
       │
       ▼
配置校验 + API 版本选择 + 规则修订快照
       │
       ▼
RuleDefinition
  ├─ 声明式 evaluator：条件树 + 动作模板
  └─ JS evaluator：模块引用 + 入口契约

OS 文件事件 ──┐
启动/补偿扫描 ┼──► 候选文件 ─► 就绪检查 ─► 持久化任务
定时规则扫描 ┤                                  │
手动触发 ────┘                                  ▼
                                      输入快照 + 规则求值
                                                │
                                                ▼
                                         ActionDraft[]
                                                │
                                                ▼
                               计划校验 / 路径展开 / 前置条件
                                                │
                                                ▼
                                          ActionPlan
                                                │
                                                ▼
                                文件锁 + 操作日志 + Executor
                                                │
                                                ▼
                             succeeded / failed / needs_review
```

这些是逻辑模块，不意味着需要独立进程、服务或独立 crate。

### 4.1 三个不同的数据模型

**RuleDefinition** 是注册信息：稳定规则 ID、触发方式、匹配范围、规则顺序、配置来源，以及声明式或 JS 求值器。

**Evaluator** 是实现条件判断和动作生成的代码。YAML 可静态表示；JS 保留为带版本的可执行模块。任意 JS 可能依赖输入、函数、循环和异步结果，不能承诺将它静态恢复为 GUI 条件树。

**ActionPlan** 是某一次、某个输入下的具体执行结果：目标路径、文件引用、动作顺序、输入条件、规则修订与风险标记。它应当可以序列化、预览、记录和测试。

概念类型：

```text
RuleDefinition {
  id,
  source,
  trigger,
  evaluator: DeclarativeRule | JsRuleRef,
  revision
}

ActionPlan {
  formatVersion,
  planId,
  ruleRevision,
  inputSnapshot,
  preconditions,
  actions[]
}
```

不将 QuickJS 的函数对象、引用或字节码直接存进数据库。数据库记录源文件修订和普通数据。

### 4.2 不要求 YAML 先生成 JS

首版 YAML 直接使用原生声明式 evaluator。JS 通过另一个 evaluator 产生相同的动作草案。两者复用 Action schema、校验器和 Executor。

为相同的输入建立 YAML / JS 等价测试，防止 glob、空值、大小和路径规则发生语义漂移。未来 GUI 只需支持声明式部分；复杂 JS 可以保留为代码，不承诺双向无损可视化。

## 五、文件触发：区分线索、就绪与重评估

### 5.1 `notify` 提供线索，不提供业务事实

`notify` 文档明确指出，网络文件系统可能不产生事件，不同编辑器保存文件时产生的事件不同，监控大量文件时也可能丢事件。[S3]

因此设计契约是：

> 事件可能重复、合并、缺失；系统根据目前可观察的文件状态决定是否处理，而不是逐条重演 OS event。

原始 create / modify / rename / delete 首版保留在诊断日志中，不作为主要稳定公共 API。尤其不要许诺跨平台可靠提供 rename 的 old/new 配对。

### 5.2 `file.ready` 的精确定义

`file.ready` 表示：**文件当前满足来源的 ready 策略，可以尝试处理。** 不表示浏览器、同步软件或其他进程已经永久写完。

建议默认策略：忽略已知临时后缀；连续观察 size/mtime；稳定达到 `stableFor` 后尝试打开；处理前再检查一次。不成功则有限退避重试。

示例的 `stableFor: "3s"` 和 `retryFor: "10m"` 是待测试的初始设置，不是正确性保证。写入方完全可能暂停 4 秒后继续写入；文件可以打开也不代表没有其他写入方。

更强的场景应由生产方协议提供：写临时文件再发布到 Inbox、生成 `.done` 标志或明确提交导入。不要把特定平台的 close-write 事件当跨平台通用完成信号。

超出等待上限应标记 `not_ready` 或进入待处理队列，不能“既然等够了就强行处理”。

### 5.3 两种扫描不能混为一谈

**补偿扫描**：寻找新出现、变更或之前遗漏的文件版本；用于恢复与最终发现。

**定时规则扫描**：对没有变化的文件也重新评估。例如“最后修改超过 7 天”，时间到了不一定产生文件事件。只用 diff 扫描，这条规则可能永远不运行。

首版提供简单 interval，无须完整 cron、时区日历或复杂调度器。JS 中涉及 `ctx.now` 的任意时间逻辑无法可靠自动推导，作者必须显式选择定时扫描。

建议的 timer 语义：进程运行时尽力调度；休眠或停机期间不保证准时；恢复后合并补做一次，不累计回放几百轮。

### 5.4 初次启用与普通重启不同

初次添加来源默认只建立已有文件基线，不自动操作历史文件。用户通过 `plan` 与显式回放选择处理存量。这个默认只针对事件型 `file.ready` 来源；显式配置 `scan` 规则意味着将按周期评估范围内的已有文件，启用前应先预览该范围。

已有来源在普通重启时要恢复任务并扫描停机期间的变化，不能每次重新把所有文件当成“初始存量忽略”。启动扫描与监听注册要处理交叉窗口，重复候选交给去重层消化。

扫描遇到磁盘离线、权限失败或根目录不可访问时，将来源标记为 unavailable；**不能把读不到的全部文件当成已删除。**

## 六、YAML Schema v1：缩小且严格

首版只提供元数据条件、简单布尔组合和动作配置，固定为约定的 YAML 1.2 子集：布尔量只接受 `true / false`，时间和单位明确写字符串。拒绝未知字段、重复键、不支持的 tag/merge 特性和超限嵌套；不要静默吞掉拼写错误。单位和时间间隔写成字符串。

`serde_yaml` 文档已明确标注停止维护；修订为优先验证 `yaml_serde`，其文档说明它是由 YAML 组织发布的持续维护分支。[S1][S2] 依然要通过本项目的 YAML 子集测试，并锁定依赖，不因名称替换就假定所有边界安全。

下面是一个拟定的完整配置；不是现成工具语法。

```yaml
schemaVersion: 1

sources:
  downloads:
    path: "~/Downloads"
    recursive: false
    ignore:
      - "**/*.crdownload"
      - "**/*.part"
      - "**/*.tmp"
    ready:
      stableFor: "3s"
      retryFor: "10m"
    reconcileEvery: "10m"

rules:
  - id: archive-pdfs
    on:
      type: file.ready
      source: downloads
    when:
      extension: pdf
    actions:
      - move:
          to: "~/Documents/PDF"
          onConflict: error
```

`onConflict` 首版只支持 `error` 和 `skip`，默认 `error`。不要一开始加入覆盖和自动寻找重名后缀；它们会扩大恢复与竞态问题。后续新增策略必须进入计划，并固定最终目标。

时间条件使用独立规则入口，例如：

```yaml
schemaVersion: 1

sources:
  downloads:
    path: "~/Downloads"
    recursive: false

rules:
  - id: archive-old-pdfs
    on:
      type: scan
      source: downloads
      every: "1h"
    when:
      extension: pdf
      modifiedOlderThan: "30d"
    actions:
      - move:
          to: "~/Documents/OldPDF"
          onConflict: error
```

同一 `when` 对象中的字段按 AND 解释。高级组合只提供有限的 `all / any / not`；不加入循环、赋值、函数或任意 JS 字符串表达式。复杂规则直接使用 JS。

路径和脚本路径以配置文件所在目录为相对基准，不依赖 daemon 当前工作目录。`~` 由应用展开为运行用户的 home；不自动执行 `$VAR`、`%VAR%` 或 shell 插值。需要部署差异时用显式参数，而不是隐藏环境依赖。

## 七、JavaScript API v1：保留灵活性，收紧歧义

### 7.1 运行语言

首版只运行标准 ESM JavaScript，文件使用 `.mjs`；也可明确将配置指定的 `.js` 按 ESM 加载。不支持 npm 自动解析、`require`、Node 的 `fs/process` 或远程 import。

模块来源只包括宿主虚拟模块和规则包内的本地模块。每次配置激活冻结并记录本地规则包源文件快照，避免 helper 改了而执行记录仍以为是同一条规则。动态 import 只能从该快照解析，不在任务运行中读取刚被修改的新 helper。

### 7.2 版本放到加载前可读取的位置

```yaml
schemaVersion: 1

sources:
  downloads:
    path: "~/Downloads"
    recursive: false

rules:
  - id: archive-pdfs
    on:
      type: file.ready
      source: downloads
    script:
      file: "./rules/archive-pdfs.mjs"
      apiVersion: 1
```

JS 中继续允许并推荐保留：

```js
export const apiVersion = 1;
```

但**manifest 中的版本才是加载决策的依据**。JS 导出值是校验断言，存在时必须一致。不能先用不确定的绑定执行整个模块，再读版本决定刚才应该加载什么。`rquickjs` 的模块接口也明确区分模块声明、求值和取得导出值。[S7]

无需为此发明 JS 解析器。宿主先读 manifest，选择对应 API，在无业务副作用的加载环境中求值模块，再检查导出。未知版本立即拒绝，不猜成最新版。

### 7.3 支持两种、且仅两种入口形态

**结构化形态**：`match(ctx) -> boolean` 与 `actions(ctx) -> Action[]`。两者均可为同步或异步函数。

**简写形态**：`run(ctx) -> Action[] | null | undefined`。空结果表示跳过，非空数组表示计划。

两种形态不能同时出现。不得存在“run 优先、其他忽略”的隐式规则。

`match` 不做 truthy 转换，返回字符串或对象属于错误；结构化 `actions` 必须返回数组。`run` 的空数组也是无动作，不认领文件。异常、超时和依赖失败不是“不匹配”，必须成为可见失败状态。

`run` 虽然沿用熟悉的名称，**仍是计划生成函数，不执行实际动作**。不要再称它为直接副作用的 escape hatch；真正的 escape hatch 是返回 `exec` 动作。

### 7.4 用显式模块，不注入一组容易冲突的全局函数

```js
import { actions as a } from "@app/api";

export const apiVersion = 1;

export function match(ctx) {
  return ctx.file.extension === "pdf";
}

export function actions(ctx) {
  return [
    a.rename(ctx.file.ref, {
      name: `archived-${ctx.file.stem}.${ctx.file.extension}`,
    }),
    a.move(ctx.file.ref, {
      to: "~/Documents/PDF",
      onConflict: "error",
    }),
  ];
}
```

`@app/api` 是拟定的宿主虚拟模块名，由 manifest 的 API 版本决定具体绑定，不是 npm 包。

简写形态：

```js
import { actions as a } from "@app/api";

export const apiVersion = 1;

export function run(ctx) {
  if (ctx.file.extension !== "pdf") return;

  return [
    a.move(ctx.file.ref, {
      to: "~/Documents/PDF",
      onConflict: "error",
    }),
  ];
}
```

### 7.5 `ctx` 的首版契约

| 字段 | 含义 |
|---|---|
| `ctx.file.ref` | 本次任务的宿主文件引用；真实操作以此为准 |
| `ctx.file.name` | 当前输入快照的文件名，包含扩展名 |
| `ctx.file.stem` | 去掉最后一个扩展名后的名字；具体边界由测试固定 |
| `ctx.file.extension` | 不带点、ASCII 小写扩展名，如 `pdf`；无扩展名为 `""` |
| `ctx.file.sizeBytes` | 字节数，跨 JS 边界检查整数范围 |
| `ctx.file.modifiedAt` | RFC 3339 时间字符串；不可获得则为 `null` |
| `ctx.file.createdAt` | 可选时间，不能假定所有平台都存在 |
| `ctx.file.path` | 可无损表示时的绝对路径字符串，否则为 `null`；不是操作身份 |
| `ctx.event.reason` | `changed / reconcile / scheduled / manual` 等标准化来源 |
| `ctx.now` | 本次求值固定的时刻，避免 match 与 actions 跨时间边界 |

文件名无法无损表示为 JS 字符串时，首版跳过脚本处理并报告明确错误，不静默替换字符后执行。Rust 内部始终保留原生路径类型。

Rust 的 metadata API 明确允许创建时间等信息不可用。[S13] 缺失信息不得伪装成当前时间或 `0`。例如 `createdOlderThan` 遇到缺失应不匹配并可解释原因。

`ctx` 为只读输入。脚本模块级变量不被承诺跨任务持久化，不开放 `ctx.state.processed = true` 之类影响执行正确性的写接口。

### 7.6 Types 不等于类型检查器

从第一版提供 `.d.ts` 和 JSDoc 示例，帮助编辑器、Agent 与外部工具。但 `app check` 首版只能承诺 schema、ESM 语法、导出契约和已知静态错误检查；不能声称能证明任意 JS 返回类型正确。

运行时仍必须校验返回 Action 数据。TypeScript 官方的 `noEmit` 说明了类型检查可与 JS 输出工具分开；这不意味着 QuickJS 或 `.d.ts` 自带检查器。[S11]

后续可以加入可选 TypeScript 转译与独立检查，但不将 Node 作为首版安装或运行依赖。

## 八、Action、Plan 与执行语义

### 8.1 首版动作收敛

首版核心为 `copy / rename / move / exec`。目录创建是 move/copy 的明确选项或内部步骤，不必立刻暴露大量独立动作。

`trash` 可在对应平台测试通过后进入早期版本；失败绝不降级成永久删除。永久 `delete`、系统通知、append CSV、webhook 和丰富第三方集成延后。CLI 日志先承担通知作用。

`exec` 留住高级扩展能力，但必须显示它是外部、不可精确预览、通常不可撤销的动作。

### 8.2 动作操作的是文件引用，不是冻结的路径字符串

以下语义必须固定：

- `rename(ref, ...)` 与 `move(ref, ...)` 更新同一个逻辑文件的当前位置。
- `copy(ref, ...)` 产生副本，但后续动作仍作用于原文件；不会悄悄把当前对象切换成副本。
- 动作严格按数组顺序执行；首版不用并行 Action，也不自动做跨步骤优化。
- `trash` 是针对该引用的终止动作，后面不能再读取或移动它。

`exec` 的文件参数使用延迟解析引用：

```js
import { actions as a } from "@app/api";

export const apiVersion = 1;

export function run(ctx) {
  return [
    a.move(ctx.file.ref, {
      to: "~/Documents/ToProcess",
      onConflict: "error",
    }),
    a.exec({
      program: "my-tool",
      args: [a.pathOf(ctx.file.ref)],
      timeout: "30s",
    }),
  ];
}
```

`a.pathOf` 生成待解析的参数描述，不是立即计算字符串。在执行第二步时，宿主填入移动后的真实路径。

原方案的 `exec("tool", [ctx.file.path])` 在 move 后可能指向旧位置，这次修订不再把它作为推荐接口。

### 8.3 Plan 是有前置条件的具体计划

计划至少绑定：来源、文件身份/版本、规则及依赖修订、解析后的目标、动作列表和计划格式版本。

`apply` 不重新运行 JS，而是执行已批准的计划；否则模型、时间或代码改变后，“批准 A、执行 B”的风险无法解释。

执行前验证：输入仍是计划所针对的文件，内容/元数据依赖未失效，来源与目标仍可访问，没有新目标冲突。条件不满足返回 `PLAN_STALE` 或明确冲突，要求重新 plan。不能偷偷换目标、跳过高风险步骤或重新调用 AI 后直接执行。

同一计划的重复 apply 返回既有状态或继续已确认可恢复的步骤，不新建一份重复任务。

文件系统不会被整个 plan 锁成静态世界。元数据指纹只是便宜检测；涉及内容判定时应绑定内容 hash 或稳定快照。执行前复核不能消除所有外部进程竞态，无法确定时停止或保留源文件。

### 8.4 默认不覆盖，并避免检查后覆盖的竞态

`std::fs::rename` 的语义包含替换既有目标，并且不能跨挂载点工作；不能直接等同于产品的安全 move。[S8]

`onConflict: error` 需要真正的 no-clobber 实现，不能只是 `exists()` 后调用可能覆盖的 rename。平台原语无法满足时，返回不支持或冲突，而不是降低保证。

跨文件系统 move 是显式多步骤过程：

```text
在目标目录创建本应用唯一临时文件
    → 从输入读取并复制
    → 校验源未变化、目标内容及所需 metadata
    → 按既定持久化策略刷新
    → 使用不覆盖策略发布目标
    → 再确认源仍对应本次操作
    → 删除源
    → 记录完成
```

过程中失败可能留下“源和目标都存在”。这应被当作可恢复状态，而不是顺手删除某一份。第一版只支持普通文件跨盘搬移，目录、特殊文件和完整 ACL/xattr 保真不在默认承诺里；不支持的能力直接报告。

### 8.5 不承诺通用事务与 Undo

SQLite 的原子提交描述的是数据库事务；它不会自动把本程序对其他文件和外部进程的操作包含进去。[S9]

本产品采用“步骤日志 + 前置/后置验证 + 必要时人工介入”，而不是跨系统事务。

| 动作 | 崩溃后的处理 | 撤销边界 |
|---|---|---|
| rename / 同盘 move | 根据文件身份和前后位置判断是否已完成 | 原位置未占用、文件未发生冲突才可能恢复 |
| copy | 校验目标是否确为本次生成 | 只可删除本应用生成且未变化的副本 |
| 跨盘 move | 检查复制、发布、源删除分别是否完成 | 不能无条件当作原子逆操作 |
| trash | 保留平台返回信息并按能力恢复 | 不保证跨平台可自动还原 |
| exec | 崩溃或超时后可能不知道外部效果 | 默认不可撤销，不盲目重跑 |

完整 Undo 延后；可追踪执行记录和崩溃后的保守恢复必须在首版。

### 8.6 `exec` 的具体边界

使用 `program + args[]`，默认不经过 shell。Rust `Command` 文档说明参数按字面值传递，同时特别提醒 Windows 的 `cmd.exe`、批处理文件采用不同参数解析规则。[S10]

明确 `cwd`、环境变量来源、超时、输出大小、退出码记录和子进程清理策略。不能假定交互 shell 的 PATH 在后台服务里一样存在。`app doctor` 应显示实际解析到的可执行文件。

需要 shell 时必须显式调用 shell，并显示平台依赖；这不是一条跨平台通用命令。传递文件路径使用 typed path 参数，不靠拼接引号。

首版要求有 `exec` 的动作序列将其放在最后；同一文件完成命令后重新观察状态。任意命令可能操作其他文件，这无法通过本程序内部锁完全约束。

超时或宿主崩溃后的外部效果标记 `needs_review`，默认不自动重试。未来只有动作提供真正可验证的幂等机制，才开放自动恢复。传入一个 operation ID 本身不让外部程序自动幂等。

## 九、状态、并发与恢复：进入 MVP

### 9.1 采用可重复求值，不承诺“恰好执行一次”

来源重新扫描、事件重复和重启恢复会导致重复候选，这是正常情况。系统目标是：**稳定可访问的文件最终会被重新发现；已完成的内置操作尽量不重复产生效果；不确定的外部效果暂停。**

只存 `processed = true` 不够。至少区分资源身份、观察到的输入版本、规则修订、任务、计划与每一步操作结果。

内容 hash 用于验证和内容缓存，但不能单独作为业务文件身份：两个不同目录下内容相同的文件，可能本来就应该分别处理。

### 9.2 最小状态表

| 表/实体 | 作用 |
|---|---|
| sources | 来源配置、基线、扫描进度、可用状态 |
| observations | 原生文件身份/路径、输入版本、最后观察结果 |
| jobs | 任务状态、关联规则修订、重试信息 |
| plans | 已生成计划、输入前置条件、批准/执行状态 |
| operations | 每步 intent、started、succeeded、failed、uncertain |

不必首版实现通用 event sourcing。一个 SQLite 数据库和有明确状态机的表已经足够。

数据库放应用的本地数据目录，不放被监控目录、网络盘或同步目录。SQLite WAL 明确不支持跨主机网络文件系统，并且数据库与 WAL 文件一起构成持久化状态。[S12]

### 9.3 首版并发策略

同一用户的数据目录只允许一个执行实例持有锁。首版可先把真正文件动作全局串行化，元数据观察和候选收集保持异步；确认瓶颈后再增加有界并发。

同一资源的任务串行；共享目标名称需要冲突控制。后续并行不能只锁源文件、不管两个任务写同一个目标。

队列必须有界；事件过载时标记来源为 dirty 并触发补偿扫描，不能静默丢弃后假装所有文件已处理。扫描应分页、有预算，不能一次加载整棵目录树进内存。

### 9.4 多规则命中的首版政策

采用明确的 `first-plan`：先按触发方式和来源选出候选规则，再在同一个文件求值任务中按配置顺序评估；首个产生非空计划的规则认领本次文件，后续规则不再执行。不要把各规则独立投递成互不协调的写任务。

不匹配或空计划继续下一条；执行失败停止本次处理，不尝试用下一条规则“补救”。未解决的部分执行也会阻塞该文件的自动新任务。

任务记录要包含本次候选规则集的修订与已认领规则。相同输入的重复事件返回既有处理结果，不能因为第一条规则已经成功，就跳过它执行第二条，否则重复事件会偷偷变成多规则串联。规则顺序变化也属于规则集修订。

这不是限制 JS 能力：需要备份、改名、移动、调用工具，可以在一个规则的动作数组中完成。多规则串联和任意工作流以后再显式设计，避免靠文件移动产生隐式流程。

### 9.5 自触发与重处理

本应用产生的 rename/move/copy 记录预期结果与文件引用，后续对应观察更新状态，默认不将自身效果开启为全新规则链。

不要靠“忽略这个路径 5 秒”实现，因为期间可能真的有外部修改。无法确认来源时仍可重新观察，但由任务历史与输入版本阻止重复效果。

规则修订纳入配置、JS 和本地模块依赖。仅改显示名称不应制造业务重处理。激活新规则或修订不自动回放全部历史文件；用户可先 plan，再显式选择回放范围。

定时扫描不能把过去的 `no_match` 永久缓存；时间条件需要重评估。已成功处理、输入未变化的同一规则版本默认不重复执行。需要每个周期都产生外部动作的规则，应将来显式配置重复政策，不偷用扫描副作用达成。

### 9.6 恢复状态机

```text
pending → evaluating → planned → applying → succeeded
               │                       │
               ├─ no_match             ├─ failed
               ├─ deferred             └─ needs_review
               └─ failed
```

`deferred` 表示文件未就绪、依赖暂不可用或内容事实缺失；不是成功，也不是永久不匹配。

操作调用前先持久化意图。重启时，已确认成功的步骤不重跑；started 但没有结果的步骤先检查后置状态。能证明完成则补记，能证明尚未执行且可安全重做才重试，其余交由 review。

配置热重载采用“完整校验后整体切换”。新配置错误时保留旧配置，输出可机器读取的失败。已在运行的任务绑定原修订；未启动的旧修订任务取消并按新配置重新求值。旧的已批准但未执行计划在修订变化后作废。

## 十、版本化：从字段升级为兼容契约

### 10.1 对用户只要求少数版本声明

- YAML：`schemaVersion`。
- JS 规则 manifest：`apiVersion`；脚本导出同名常量可作为断言。
- 应用版本：独立发布，不用让规则跟随每个应用版本改写。

API 使用整数主版本是合理的，但同一版本“只增不删”仍不充分：新应用新增的方法，旧应用不一定有。因此以后对可选能力提供明确的 `requires` 检查，或在必要时提供最低应用版本约束；不要假定 `apiVersion: 1` 在所有历史 v1 宿主上功能完全相同。

### 10.2 兼容包含行为，不只是函数名

扩展名是否带点、copy 后当前对象是谁、冲突默认值、路径展开规则、时区与日期类型，都属于 API 语义。

如果默认冲突政策从覆盖改为报错，这不只是改函数签名。适配层必须将旧默认值显式翻译到新计划，或者要求迁移。不能保证每一次重大变更都能用一个便宜的薄 adapter 解决。

每个公开 API 版本保存固定 fixtures、schema、类型声明和 action-plan 黄金样例。正式稳定之前只承诺实验版本迁移便利，不承诺无限期兼容。

### 10.3 其他版本由应用管理

持久化 Plan、CLI JSON、数据库 schema 和内容缓存分别有内部/输出格式版本。用户不必手动填写它们，但应用升级必须识别并迁移或失效处理。

缓存键至少包括内容版本、提取器/模型版本、参数和输出 schema。QuickJS 字节码只可作为与运行时构建绑定的可丢弃缓存，不作为跨版本公开规则格式；`rquickjs` 的字节码加载是需要调用方确保有效性的 unsafe API。[S7]

同一 API 版本仍需随运行时升级重跑兼容测试。API 主版本不能替代依赖版本锁定。

## 十一、JS Runtime 与最小可靠性保护

### 11.1 `rquickjs` 保留，但先通过构建门槛

`rquickjs` 提供 Promise/Future 互操作与自定义模块加载；同时上游明确指出它包含 C 库和平台绑定，不能因为 Rust 支持某 target 就假定它必然可编译，当前平台表也有测试覆盖与 experimental 标记。[S4]

因此它是**首选待验证依赖**，不是无需验证的既定完成项。

### 11.2 不把 JS 值随意塞进 Tokio 多线程任务

给 JS evaluator 一个明确的运行边界：初期专属 worker 线程、拥有自己的运行时和事件循环，宿主服务通过通道接收普通 Rust 数据。

`rquickjs` 的运行时 Send/Sync 支持与 feature 相关，Module 等值仍有生命周期和线程限制；不要推断“有 async 支持就可以任意跨线程传 JS 对象”。[S5][S7]

首版每个求值任务使用隔离的运行环境，不承诺模块全局变量跨文件保留。性能优化不能悄悄改变规则状态语义。

### 11.3 资源预算不是权限系统

需要分别设置：JS 执行预算、JS 内存/栈限制、宿主调用超时、任务总时长、动作数量、输出大小。未来 OCR/模型时间不应塞进同一个很小的 JS 计算时限。

`rquickjs` 有 interrupt handler 和内存限制接口，但文档明确说明：采用自定义 allocator，包括相应 `rust-alloc`/`allocator` 路径时，`set_memory_limit` 可能是 no-op。[S5][S6] 必须对最终 feature 组合写压力测试，不能只调用函数就认为限制生效。

中断解释器不代表能打断任意阻塞的 Rust/C 调用，JS 内存上限也不覆盖所有宿主分配。首版不在同步宿主函数中执行长期阻塞工作。未来 PDF/OCR/本地模型或不可靠原生库可放进可终止的子进程。

独立进程不必第一天就实现；但若技术验证无法确保错误脚本不会拖死主服务，它将成为发布门槛，而不是继续宣称可靠。

### 11.4 信任模型保持简单且诚实

初期规则视为用户明确安装的可信本地代码；`exec` 能以当前用户权限运行程序。应用不是恶意插件的安全沙箱，不从监控文件或互联网自动发现并执行脚本。

规则目录、数据目录与 Inbox 分离。Agent 生成的文件内容、PDF 文本和 OCR 结果是数据，不应自动变成 shell、JS 源码或新的授权指令。

不做繁重授权弹窗，但保留 no-clobber、任务预算、受控默认行为和可见的外部命令计划。

## 十二、CLI 与 Agent 工作流

首版一份二进制，建议命令如下：

| 命令 | 语义 |
|---|---|
| `app check` | 检查配置、版本、ESM 语法/加载与规则入口，不执行业务动作 |
| `app test` | 用固定文件/metadata fixtures 检查匹配与 ActionPlan |
| `app plan <path>` | 对指定输入生成计划，不执行文件动作或外部命令 |
| `app apply <plan-id>` | 复核并执行已保存计划，不重新求值 JS |
| `app daemon` | 长驻监听、扫描、恢复和执行 |
| `app status` | 来源、待处理、错误、扫描时间与活动修订 |
| `app history` | 查询实际操作结果及未确定状态 |
| `app doctor` | 检查路径、权限、依赖程序、数据库和平台能力 |

用户尚未开启 daemon 时，独立 apply 可取得同一数据目录的执行锁；daemon 已运行时首版可明确拒绝竞争性写实例。先不为全部命令实现复杂 IPC。读命令使用一致的状态快照。

`--json` 输出稳定包络，例如 `formatVersion / ok / data / errors`；stdout 只放机器数据，日志写 stderr。错误提供 code、ruleId、source、阶段、文件行列与建议，不要求 Agent 解析自然语言报错。

Agent 的推荐流程为：

```text
读取 API schema 与规则
    → 修改草稿
    → check
    → fixture test
    → plan
    → 展示具体差异
    → 用户授权或已有启用策略
    → apply / 激活规则
```

schema 和 `.d.ts` 为宿主权威契约生成或由同一测试维护，避免 Rust、YAML、JSON schema 与类型声明各自漂移。

CLI 预览不应声称“一定免费、完全无 IO”。它可能读文件、写本地日志和缓存。未来加入 OCR/AI 后，应区分默认的无远程提取预览与显式 `--enrich`；没有事实时返回 `NEEDS_FACTS`，不能为了展示漂亮计划偷偷上传内容。访问云盘占位文件还可能触发系统下载，支持范围要另行标注。

## 十三、跨平台范围与工程组织

### 13.1 初版发布目标

优先验证 macOS arm64、Windows x64、Linux x64；macOS x64 和 Linux arm64 可按实际用户需要追加。不是宣称其他 Rust target 已受支持。

CI 必须在各原生系统上跑文件操作测试，而不仅是 cross-compile。锁定 Rust toolchain、Cargo.lock、C 编译器组合和最低运行环境，发布产物记录这些信息。

Windows MSVC 是优先验证路线，但必须使用锁定的 `rquickjs` 版本实际构建运行；上游目标表的 experimental/未测试状态是风险线索，不是本产品已经验证通过的证明。[S4]

### 13.2 平台差异必须有产品政策

| 场景 | 首版政策 |
|---|---|
| 系统目录与用户目录 | 只处理明确配置的普通用户目录；不默认扫描整个 home |
| 符号链接、junction、reparse point | 默认不递归跟随；不能只做字符串前缀判断 |
| 文件锁、权限、磁盘满 | 可见失败与有限重试，不丢弃源文件 |
| UNC / NAS / 同步盘 | 初期标注条件支持，不承诺与本地磁盘同等事件可靠性 |
| 大小写、Unicode、保留文件名 | 按目标文件系统校验，不把所有路径简单转小写 |
| 不可表示的原生文件名 | 明确跳过并报错，不做有损路径转换 |
| metadata 保真 | 明确哪些字段保留；不默认承诺全部 ACL、扩展属性和流 |
| 日期与系统时区 | 时间戳固定格式；本地展示与规则时间分开 |

Windows 文件名存在保留字符、设备名及尾随点/空格等规则，不能用一个跨平台正则想当然地覆盖全部情况。[S14]

路径 sanitize 不应默默改变已经批准的目标。需要清理时先生成候选名称放进计划，再做目标冲突检查。

### 13.3 单二进制不等于无平台依赖

首版不要求 Python/Node 运行时。但嵌入 QuickJS、SQLite 及未来 PDF/OCR 库仍涉及原生构建、许可证审计、漏洞升级和分发测试。[S4]

后台先支持 `app daemon` 前台运行；产品化再提供用户级服务安装。避免默认使用 root/Administrator 常驻。服务启动、日志位置、工作目录、PATH、退出重启与升级行为都要被测试，不仅是 watcher API。

### 13.4 减少过早拆分

建议最多先用三个 crate，而不是按每个抽象建一个 crate：

```text
crates/
  automation-core/      # 规则、任务、计划、执行、状态、平台模块
  automation-js/        # rquickjs 与宿主绑定
  automation-cli/       # CLI 与 daemon 子命令

examples/
  yaml/
  js/

tests/
  fixtures/
  recovery/
  platform/
```

JSON/YAML 解析、SQLite 和平台适配可以先作为模块。到真实复用或编译边界出现时再拆。保留明确职责即可，不为几年后的所有可能功能建立一堆空 trait。

## 十四、文档与小模型：只保留必要边界

第一版不实现 PDF/OCR/发票模型，只避免让规则求值依赖某个固定提供方。届时内容能力通过宿主服务进入 JS，接口正式设计后再加，当前不把几十个未来方法承诺成 API v1。

内容处理阶段重点不是一个 `confidence > 0.9`，而是下列契约：

**按需提取与缓存。** 缓存键绑定内容版本、提取器/模型、参数和 schema。相同任务的重复请求共享正在运行的结果；不可只按路径缓存。

**区分事实缺失与不匹配。** 原生 PDF 文本、OCR、字段提取都可能失败或部分成功。缺失金额不是 0，缺失日期不是今天。必要字段未验证时进入 review。

**PDF 不能只看有没有 text layer。** 后续提取策略需要识别混合扫描/文字页面、不可用文字层和加密/损坏文档；原生提取优先只是策略起点，不是所有页面的唯一分支。

**精确数据类型。** 文档日期如 `"2026-09-01"`，不是一会儿字符串、一会儿 `doc.date.year`。金额采用十进制字符串加币种，例如 `{ amount: "132.50", currency: "USD" }`，运算由精确金额工具负责，而不是直接依赖 JS 浮点结果。

**证据与校验。** 字段记录来源页/区域/原文、提取器版本与校验结果。模型输出的自报 confidence 不当作校准概率；阈值要由目标样本验证。JSON schema 合法只代表形状正确，不保证金额或商家正确。

**保护执行可复现性。** `plan` 保存提取结果及版本，`apply` 不重新问模型决定另一套动作。需要刷新时生成新计划。

**隐私与成本。** 本地是默认处理政策；云模型或用户 endpoint 必须明确启用，缓存和审计有保留/删除策略。文件内容不能作为执行代码。网络费用、内容上传与文件写操作分开说明。

未来本地模型建议优先试独立 worker / sidecar，与核心通过普通结构化数据交换。不要现在绑定 llama.cpp 或承诺所有硬件上的推理速度。

## 十五、重新划定 MVP 与演进门槛

### 阶段 A：技术原型，先证明依赖可用

在目标桌面系统验证 `rquickjs` ESM、async、版本装载、超时、内存限制和重复任务隔离；验证 `notify` 常见保存/rename 行为及原生文件操作。

交付门槛是测试通过与风险记录，不是“Rust 能编译”。若 Windows 链路或脚本终止策略不可靠，先解决，不继续堆文档能力。

### 阶段 B：可信的文件自动化 MVP

包括 YAML、JS 两种规则，file.ready、手动输入、简单 interval 扫描，元数据条件，copy/rename/move/exec，SQLite 最小状态、任务恢复、单实例锁、重复处理防护、目标冲突检测、check/test/plan/apply/daemon/status/history。

**可靠性不是下一阶段的装饰。** 首版可以少动作、少格式、低并发，但不能在真实文件上不记录半途失败。

默认 no-clobber、初次存量不自动处理、异常不当作不匹配、exec 不盲目重试。

### 阶段 C：产品化和一个真实文档场景

先完成安装/升级/服务运行、诊断包、更多平台故障测试。再选择一个具体文档需求加入文本提取、结构化输出和人工核对，而不是同时开发简历、合同、银行账单和发票包。

完整 Undo、第三方集成、OCR、更多动作按照真实用户阻力排序。

### 阶段 D：验证后的智能能力

只有当处理效果、用户留存和成本数据支持时，才引入更多分类器、模型提供方与本地推理。先验证规则是否真的节省工作，不按模型种类规划商业版菜单。

## 十六、首版验收与故障测试清单

| 测试 | 预期结果 |
|---|---|
| 下载中途暂停超过 stableFor | 不承诺完整；后续变化使旧计划失效或延后处理 |
| 大量重复/乱序文件事件 | 同一已确认文件版本不重复产生成功动作 |
| 主动丢弃 watcher 通知 | 补偿扫描可以发现稳定可访问的漏项 |
| 文件不变，但年龄条件到期 | 定时规则扫描重新匹配 |
| 目标在 plan 后被其他程序创建 | apply 冲突，不覆盖、不悄悄重命名 |
| 文件内容在 plan 后改变 | 依赖失效，拒绝旧计划 |
| rename 后继续 move/exec | 使用同一 FileRef 的当前位置 |
| copy 后再 move | 移动原文件，副本不被误当当前对象 |
| move 完成后、数据库记成功前崩溃 | 恢复检查后置状态，不直接重复搬移 |
| 跨盘复制中断或磁盘满 | 保留源与明确临时状态，不丢文件 |
| exec 启动后崩溃或超时 | 标记外部效果不确定，不自动再执行 |
| 两条规则命中同一文件 | 严格采用 first-plan，失败不切换备用规则 |
| 第二个执行实例启动 | 锁冲突明确退出，不并发操作同一数据目录 |
| 规则加载错误、API 不支持 | 拒绝新修订，旧激活配置保持可用 |
| JS 无限循环/未结束 Promise/超量结果 | 有限资源内终止或任务失败，服务仍可用 |
| 依赖 helper 更新 | 规则修订变化，旧待执行计划可识别失效 |
| 来源磁盘离线/权限被撤销 | 来源 unavailable，不推导大批删除 |
| Windows 名称、中文、空格、长路径 | 可解释且无数据损坏；不支持则明确拒绝 |
| YAML 与 JS 表达同一规则 | 固定 fixtures 下产生等价 ActionPlan |
| 应用升级与数据库迁移 | 可备份/恢复，旧 fixture 兼容性可验证 |

性能基准应记录文件数、文件大小、磁盘与系统版本；测空闲占用、批量导入吞吐、扫描时间、状态库增长与错误恢复时间。当前没有实测，不在报告中承诺“低于若干毫秒”或“几十 MB 内存”。

## 十七、商业判断的修订

此前将“发票识别 + 自动归档”直接描述为能卖的产品，证据不足。本次改为可验证假设：

> 某类用户愿意为可核对的文档字段提取、稳定归档和已有工具之间的数据流转付费。

Agent + YAML/JS 是配置入口，不自动构成壁垒。没有 GUI 的产品早期更容易服务能使用 Agent 或命令行的用户；不要把他们的接受度直接当作会计、行政或普通消费者的接受度。

建议先用个人真实文件流程打磨可靠性，同时从少量潜在付费用户获得脱敏样本、现有操作步骤和试用反馈。尤其用户本人不需要发票功能，更应在投入专用提取器前确认目标人群和持续使用意愿。

收费试验关注：每周省多少人工、异常需要改几次、部署与支持花多少时间、处理成本、误移动/错误数据的容忍度，以及是否愿意为试点付费。文件监听和模型接入本身不构成收入证据。

不开出没有验证的价格表，也不现在决定所有基础功能免费、所有 Document Pack 收费；这些选择要服从获客、支持与成本数据。

## 十八、最终决策与待验证项

**现在可以定下的：** Rust；桌面 CLI/Agent；YAML + ESM JS；声明与执行分离；FileRef；最小任务与操作日志；明确版本选择；no-clobber；first-plan；标准化错误与计划。

**先验证再锁定的：** `rquickjs` 的具体版本/feature/Windows 工具链；`yaml_serde` 子集表现；跨盘 move 的原生实现；脚本预算的真实效果；是否需要独立 worker 进程；文件 ready 默认参数。

**明确后置的：** 通用 Undo、复杂多规则链、TS 内置工具链、OCR/AI 提供方、文档商业包、插件市场、GUI、移动端。

推荐依赖基线是 `notify + rquickjs + serde/yaml_serde + SQLite`，Tokio、clap、tracing、glob/regex 等作为实现候选。不要在原型验证前把所有可选 crate 写成不可变架构决策。

**总的调整是：功能更克制，执行契约更具体。先做“能放心让它操作真实文件”的工具，再做“能理解更多文件”的产品。**
